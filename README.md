## Overview

External signing is a GroupDocs.Signature capability for Python via .NET that hands the
document digest to code you provide instead of signing with a private key the application
holds. This repository pairs it with the HashiCorp Vault Transit engine: the RSA key is
created inside Vault, the Python process never receives it, and the only value that crosses
the wire is a 32-byte SHA-256 digest. What comes back is an ordinary signed PDF that a reader
verifies like any other.

Everything here runs against Vault in dev mode from the included `docker-compose.yml`, so the
whole pipeline is two commands on a laptop. It is written for developers who have to answer a
security review about where the signing key lives, and for anyone porting the same design to
an HSM or a cloud KMS, which plug into the same hook.

## Technology Stack

- **Platform**: Python 3.11 and 3.13, through the Python via .NET bindings
- **Product**: GroupDocs.Signature for Python via .NET 26.10.0
- **Key manager**: HashiCorp Vault 2.2.1, Transit secrets engine
- **Certificates**: asn1crypto 1.5.1, used to assemble the X.509 structure
- **HTTP**: `urllib.request` from the standard library, no HTTP dependency

## Problem Statement

The usual way to sign a PDF in Python is to give the library a PFX file and its password. It
works, and it means a copy of the private key is on the application host: in a file, in a
container image, in a secret store that eventually writes it to a disk, or in memory where a
crash dump can reach it. Whoever obtains that file and the password can sign in your name
until somebody revokes the certificate.

Teams that already run Vault want the signing key in Vault, where it is created, versioned,
audited and never exported. That only works if the signing library can be told to ask
something else for the cryptography. A library that insists on loading a private key cannot
participate at all, and most PDF tooling for Python is built that way.

Vault Transit is a good match for the other half of the problem, because it signs a digest
without ever seeing the document. The question is what connects the two.

## Solution Overview

`DigitalSignOptions.custom_sign_hash` is the connection. GroupDocs.Signature does everything
up to the cryptography: it prepares the PDF, works out which bytes the signature covers,
hashes them, and then calls your code with that digest. You return signature bytes from
wherever you like. The library embeds them with the certificate and writes the file.

Key technical points in this implementation:

- **Nothing to export**: the RSA-2048 key is generated by Vault and stays there; `transit/sign`
  is the only operation the application needs.
- **Pinned key version**: the certificate and every signature use one key version, read once,
  so a rotation cannot silently split them.
- **Prehashed requests**: the digest goes to Vault as a hash, with `prehashed = true`, and
  Vault signs it as it is.
- **Standard library HTTP**: the Vault client is 160 lines of `urllib`, so there is nothing to
  audit beyond it.
- **Two rights in production**: the included policy allows reading the key and signing with it,
  nothing else.

## Getting Started

### Installation

```bash
python -m venv .venv
pip install -r requirements.txt
```

Activate the environment before installing: `.venv\Scripts\activate` on Windows,
`source .venv/bin/activate` on Linux and macOS.

### Configuration

1. Start Vault in dev mode with `docker compose up -d`. The container listens on
   `http://localhost:8200` with the root token `dev-only-token`.
2. Run `python sign_pdf_with_vault.py`. On the first run it enables Transit and creates the
   RSA-2048 key `pdf-signing-key`; later runs reuse it.
3. To sign with a licence, replace `REPLACE_WITH_YOUR_LICENSE_PATH` in `sign_pdf_with_vault.py`
   with the path to your `.lic` file. Never commit it; `.gitignore` already excludes `*.lic`.

Everything else is configurable without touching the code:

| Setting | Where | Default |
|---------|-------|---------|
| Vault address | `VAULT_ADDR` environment variable | `http://localhost:8200` |
| Vault token | `VAULT_TOKEN` environment variable | `dev-only-token` |
| Key name | `KEY_NAME` in `sign_pdf_with_vault.py` | `pdf-signing-key` |
| Input PDF | `Resources/document.pdf` | |
| Output PDF | `Result/signed_document.pdf` | |

A successful run prints the key version, the certificate step, the output path and
`Signature valid: True`, and exits with code 0.

### File Descriptions

- `sign_pdf_with_vault.py` - reads or creates the Transit key, builds the certificate, signs
  and verifies, and prints each step. It also deletes a partial output file when signing fails.
- `vault_signer.py` - the `custom_sign_hash` implementation plus the map from GroupDocs hash
  algorithms to Vault names. This is the whole integration surface.
- `vault_transit_client.py` - `read_key`, `enable_transit`, `create_key` and `sign_hash` over
  `urllib`, with Vault's own error text preserved in the exception message.
- `certificate_helper.py` - assembles the to-be-signed certificate around the Vault public key
  and has Vault sign its digest, so no private key is involved anywhere.

## Code Implementation

### Implementation: the external signer

The method GroupDocs.Signature calls once per signature. It receives a digest, not a document,
and returns raw signature bytes.

```python
def custom_sign_hash(
    self, signable_hash: bytes, hash_algorithm: HashAlgorithm, signature_context
) -> bytes:
    vault_hash_algorithm = _VAULT_HASH_ALGORITHMS.get(hash_algorithm)
    if vault_hash_algorithm is None:
        raise ValueError(f"Hash algorithm {hash_algorithm!r} is not supported.")
    return self._vault.sign_hash(
        self._key_name, self._key_version, bytes(signable_hash), vault_hash_algorithm
    )
```

#### Technical Details

`signable_hash` is already the digest of the PDF's signed byte range, 32 bytes for SHA-256, and
it is exactly the value the signature has to cover. `hash_algorithm` is the algorithm the
library really used, so the map is one to one: SHA256 to `sha2-256`, SHA384 to `sha2-384`,
SHA512 to `sha2-512`, SHA1 to `sha1`. An unknown value raises `ValueError` rather than guessing.
`signature_context` is unused here.

Key components: `_VAULT_HASH_ALGORITHMS` for the name mapping, and `VaultTransitClient.sign_hash`
for the request. Output: the raw signature, 256 bytes for an RSA-2048 key.

### Implementation: the Vault sign request

The only Vault call that matters for the signature itself.

```python
request = {
    "input": base64.b64encode(digest).decode("ascii"),
    "key_version": key_version,
    "hash_algorithm": hash_algorithm,
    "prehashed": True,
    "signature_algorithm": "pkcs1v15",
}
data = self._request("POST", f"/v1/transit/sign/{key_name}", request)["data"]
# Vault returns "vault:v<version>:<base64 signature>".
return base64.b64decode(data["signature"].rsplit(":", 1)[1])
```

#### Technical Details

Three fields decide whether the PDF verifies. `prehashed` tells Vault the input is already a
hash; without it Vault hashes the digest again and the signature covers the wrong value.
`signature_algorithm` has to be `pkcs1v15`, because Vault defaults to PSS for RSA keys while the
PDF signature is sha256WithRSAEncryption. `key_version` pins the signature to the version in the
certificate.

Vault checks the digest length against `hash_algorithm`, so a mismatch fails loudly with
`500 crypto/rsa: input must be hashed message`. A token without `update` on
`transit/sign/{name}` gets `403` and the client raises `VaultError` carrying Vault's message.

### Implementation: a certificate for a key you cannot export

A PDF signature carries an X.509 certificate so a verifier can find the public key. Vault will
not hand over the private half, so the certificate is built around the public half and signed by
Vault itself.

```python
digest = hashlib.sha256(tbs_certificate.dump()).digest()
signature = vault.sign_hash(key_name, key.version, digest, "sha2-256")

certificate = x509.Certificate({
    "tbs_certificate": tbs_certificate,
    "signature_algorithm": algorithm,
    "signature_value": signature,
})
return certificate.dump()
```

#### Technical Details

This is the first of two Vault sign requests per run; the second one signs the PDF. `asn1crypto`
assembles the `TbsCertificate` with the Vault public key, `CN=Vault Transit Signer` as subject
and issuer, and a digital-signature key usage. Validity starts one day before now on purpose: a
PDF reader compares the signing time with the start date, and a certificate minted a second
before signing has been reported by Acrobat as "expired or not yet valid" on a machine two hours
east of UTC.

Output: the certificate as DER bytes. In production, replace it with one a CA issues for the
same key; Transit can sign a CSR through `transit/keys/:name/csr`.

### Implementation: signing the PDF

```python
certificate_object = DigitalVerifyOptions(
    certificate_stream=io.BytesIO(certificate)).certificate
digital_signature = DigitalSignature(certificate=certificate_object)
digital_signature.sign_time = datetime.now().astimezone()

options = DigitalSignOptions()
options.signature = digital_signature
options.custom_sign_hash = signer
options.hash_algorithm = HashAlgorithm.SHA256
options.reason = "Document signed with HashiCorp Vault Transit"
options.location = "HashiCorp Vault"

with gs.Signature(str(input_pdf)) as signature:
    signature.sign(str(output_pdf), options)
```

#### Technical Details

Two lines here are Python-specific. The binding has no X.509 type of its own, so the certificate
object is taken from `DigitalVerifyOptions`, which loads a public-only certificate; passing a
path or stream to `DigitalSignOptions` instead fails with "Specified certificate doesn't contain
private key", a confusing message when the whole design is that no private key exists.

`sign_time` is deliberately time-zone aware. A tz-aware value is written into the PDF with its
offset, while the default UTC time and a naive local time are written without one, and readers
then interpret them in their own zone. The sample also sets a visible signature box through
`vertical_alignment`, `horizontal_alignment`, `margin`, `width` and `height`.

### Implementation: verifying the result

```python
options = DigitalVerifyOptions(certificate_stream=io.BytesIO(certificate))
with gs.Signature(str(signed_pdf)) as signature:
    return signature.verify(options).is_valid
```

#### Technical Details

The check is cryptographic: `is_valid` is False when the document changed after signing, or when
the signature came from a different key than the certificate holds - a different Vault key
version, for instance. Verifying without passing the certificate does not tie the result to the
expected signer, so the sample always passes it.

A self-signed certificate satisfies this check. Acrobat additionally wants a trusted issuer and
reports the signer's identity as unknown without one, which is a trust question rather than a
cryptographic failure.

## Which part of this is easiest to get wrong?

The digest handling. A wrong `hash_algorithm` name fails loudly with Vault's 500, so you fix it
in a minute. A missing `prehashed` flag fails silently: Vault hashes the digest again, the PDF is
written without any error, and nothing reveals the problem until somebody verifies the file. The
certificate and the policy can be corrected later; a batch signed over the wrong value cannot.

## Best Practices

When adapting this repository, a few habits save real debugging time.

Read the key version once and use it for both the certificate and every signature. After
`transit/keys/:name/rotate` Vault signs with the newest version unless told otherwise, and a
certificate for version 1 plus a signature from version 2 produces a PDF with no error and no
valid signature.

Give the application a policy, not a root token. `vault/sample-signer.hcl` grants read on the
key and update on `transit/sign`; with that token the sample signs exactly as before, while
rotating or creating keys returns `403 permission denied`. Pair it with a short-lived token from
an auth method such as AppRole rather than a static one.

Use HTTPS outside a local test, and trust Vault's CA properly. Dev mode is in-memory, plain HTTP
and a fixed root token, which HashiCorp says never to run in production.

Enable an audit device. One of the quiet benefits of this design is that every signature becomes
a logged Vault request, which is far easier to produce for an auditor than filesystem access logs
for a PFX file.

Keep the failure path honest: delete the partial output when signing fails, as
`sign_pdf_with_vault.py` does, so no half-written PDF is mistaken for a signed one.

When I compared this port against its .NET sibling, the only place where the two APIs genuinely
diverge is the certificate hand-off - .NET has `X509Certificate2`, Python routes the object back
out of `DigitalVerifyOptions`. Everything else, including the Vault request body, is the same
design in two languages.
